### DOWNGRADED — ens_notifications scope (Phase 1 under-reported active consumers)

**Phase 1 finding:** ens_notifications is "TRANSITIONAL" — written by the legacy blast path, read by reports and dashboardController.

**Independent verification:** Phase 1 was correct that the table is transitional but significantly underestimated the scope of active non-legacy consumers:

1. **`GET /reports/ens`** (routes/v1/reports.js lines 430-475) — This is the **active, paginated, unified ENS report** endpoint consumed by the `EnsReport` page. It reads exclusively from `ens_notifications`. Phase 1 labeled this endpoint as ACTIVE and implied it used ens_campaigns data. It does not. The campaign-engine backed report is at a *separate* endpoint: `/reports/ens-campaigns`.

2. **`GET /reports/ens/:notificationUuid`** (routes/v1/reports.js lines 477-517) — Detail view for a single ENS notification. Reads from `ens_notifications` and `ens_notification_deliveries`. Consumed by `EnsReport` detail drilldown.

3. **`dashboardController.js`** lines 32, 175, and 197 — Dashboard metrics (active incidents, chart data) all query `ens_notifications`. The main dashboard actively depends on this table.

4. **`ensController.listNotifications`** (ensController.js lines 326-341) — `GET /ens/notifications` used by the frontend `api.ens.notifications()`. Active endpoint.

**Consequence:** `ens_notifications` cannot be retired without rewriting:
- dashboardController (3 queries)
- EnsReport page and its backend endpoint
- ensController.listNotifications
- The four legacy report pages
- ensController.createNotification (UI blast write path)
- The /internal/ens/notifications/* endpoints (legacy Lua write path)

This is a substantially larger migration than Phase 1 implied.

### Current Architecture Assessment

The campaign engine (`ens_campaigns` / `ens_campaign_destinations`) handles all outbound call
orchestration when triggered by `ens_blast_trigger.lua`. However, the reporting and dashboard layers
have NOT been migrated. Both the active `EnsReport` page and the `dashboardController` still read
from `ens_notifications`.

The dual-table situation is:
- **New writes go to:** `ens_campaigns` (via campaignEngine) — all outbound delivery state
- **Old writes still go to:** `ens_notifications` (via UI blast endpoint and legacy Lua path)
- **Reports read from:** `ens_notifications` — including the non-legacy EnsReport page
- **Campaign reports read from:** `ens_campaigns` — separate endpoint `/reports/ens-campaigns`

There is no unified view. Users who trigger blasts via the UI and then view `EnsReport` see data
from `ens_notifications`. Users who view the campaign dashboard see data from `ens_campaigns`.
Blasts triggered by Lua (ens_blast_trigger.lua → campaign/start) do NOT appear in EnsReport at all.

### Gap Analysis

**Cannot retire ens_notifications until:**
1. EnsReport page is rewritten to read from `ens_campaigns`
2. dashboardController is rewritten to read from `ens_campaigns`
3. ensController.createNotification is rewritten to create an ens_campaigns record
4. ensController.listNotifications is rewritten to read from ens_campaigns
5. Historical ens_notifications data is either migrated or accepted as lost from reports
6. All four legacy report pages that read ens_notifications are removed

**Migration strategy:**
- Phase A: Extend `/reports/ens` to read from `ens_campaigns` (may UNION with ens_notifications for historical data)
- Phase B: Rewrite dashboardController to read from `ens_campaigns`
- Phase C: Deprecate the UI blast POST (or redirect it to create a campaign)
- Phase D: Remove legacy report pages
- Phase E: Drop ens_notification_deliveries, then ens_notifications

## media_files.duration_seconds vs duration_sec

**Canonical column:** `duration_sec` (type NUMERIC(8,2)) — written and read by:
- `mediaLibraryController.js` (reads and writes)
- `recordingController.js` (reads and writes)
- `deploymentController.js` (reads RIFF file duration)
- `reports.js` (reads for recording detail)
- `validateSchema.js` (listed as expected column)
- `campaignEngine.js` (reads `campaign_duration_sec` — different table)

**Legacy column:** `duration_seconds` (type INT) — never written, never read by any controller.
The occurrences of `duration_seconds` in reports.js are computed aliases: `EXTRACT(EPOCH FROM ...)::INT AS duration_seconds` — these do NOT reference the media_files column.

**Verdict:** `duration_seconds` is safe to drop. No migration of data is required (column is always NULL since no code ever writes it).

```sql
ALTER TABLE media_files DROP COLUMN IF EXISTS duration_seconds;
```
